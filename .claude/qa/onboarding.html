Your First Test Cases

This repo has an agent that reads a Jira ticket, works out what needs testing, and creates real Xray tests for you. It takes about 40 minutes to set up, and most of that is waiting on other people for access. Work through it top to bottom — each step assumes the one before it worked.

What this actually does

Writing test cases by hand is slow, and the slowest part isn't the thinking — it's typing forty near-identical tickets into Jira. This tooling does the typing. You still make every real decision.

  1. You askPoint the agent at a ticket, e.g. EC-14
  2. It readsThe ticket, the design handover, and the real site code
  3. It draftsA plan file on your machine — nothing in Jira yet
  4. You approveRead it, change what's wrong, say go
  5. A script pushesReal Xray tests appear in EC

Step four is the important one. Nothing reaches Jira until you say so. The agent drafts, you decide. If a plan is wrong, you edit a file — no cleanup in Jira needed.

Three places things live

Worth knowing up front, because it explains why some things are in git and some aren't.

WhereWhat's kept there
The git repo The agent itself, the scripts, and the plans. This is the master copy of your test content.
Jira & Xray The published tests that people actually run, plus their execution history.
Jira labels Each test carries a hidden-ish id like BRANDS-TC-01. That's how the tooling recognises a test it already made, so re-running never creates duplicates.
Read this before you write anything

This repo is public on GitHub, and plan files are committed to it. Every word you put in a test step is world-readable and permanent once pushed. Write steps about behaviour — "the label shows the new text" — and keep anything genuinely confidential out of them.

Ask for these first

Three things need another human, so send the messages now and set up while you wait.

1 · Push access to the repo

The repo is public, so you can clone it today without asking anyone. You only need an invite to push your own changes. Ask Robert to add you as a collaborator on robert-balan/adobe-ema-test.

2 · Jira and Xray access

You need an account on unileverfoodsolutions.atlassian.net with the EC project, and permission to create issues, edit them, add comments and link them. You also need Xray enabled for your user.

3 · Access to DA (da.live)

DA, short for Document Authoring, is where the site's pages are actually written. You need it because the agent creates the little test pages your steps link to. Ask for access to foodsolutions-04 / ufs, and mention you'll be writing into /drafts/qa/ — a corner set aside for QA that never goes near the live site.

4 · Your own Xray API key

This one has a catch worth understanding. Xray Cloud keeps test steps in its own database, not in Jira, so the normal Jira connection can't write them. The scripts need a separate Xray key.

Creating one needs Jira/Xray admin rights, so an admin has to do it for you: settings gear → Apps → Marketplace Apps → Xray → API Keys → Create API Key, with your name in the User field. They should send you the Client ID and Client Secret through a password manager — not Slack, not email. The secret is shown once and can never be retrieved again.

Don't borrow someone else's key

A key is tied to one Jira user, and every test it creates is attributed to that person. Use a colleague's key and your work shows up under their name.

Setting up

Six steps. Each shows the command to run and what a working result looks like — if what you see doesn't match, stop there rather than carrying on.

Check you have Node and jq

Two minutes

The push script runs on Node, and the Xray helper uses jq to handle JSON. Both are probably already there.

Terminal
node --version
jq --version
You should see

A version number from each, Node v18 or newer. If jq is missing: brew install jq.

Clone the repo

One minute

Terminal
git clone https://github.com/robert-balan/adobe-ema-test.git
cd adobe-ema-test
You should see

A folder containing .claude/. The agent, the scripts and any existing test plans all arrive with the clone — there's nothing extra to install for the QA work. (npm install is only needed if you're editing the website itself.)

Store your Xray key

Five minutes · needs the key from step 3 above

Put the two values in your macOS Keychain, where they're encrypted at rest. Using -w with no value makes it prompt, so the secret never lands in your shell history.

Terminal · paste each value when prompted
security add-generic-password -a "$USER" -s xray-client-id -w
security add-generic-password -a "$USER" -s xray-client-secret -w

Then add these lines to your ~/.zshrc so every new terminal picks them up:

~/.zshrc
export XRAY_CLIENT_ID="$(security find-generic-password -a "$USER" -s xray-client-id -w 2>/dev/null)"
export XRAY_CLIENT_SECRET="$(security find-generic-password -a "$USER" -s xray-client-secret -w 2>/dev/null)"

Open a new terminal window so those take effect.

Never put these in a file inside the repo

The repo is public. A committed secret is scraped by credential scanners within minutes. Not in .mcp.json, not in settings, not in a comment.

Store your DA token

Five minutes · you'll redo this every day or so

DA doesn't hand out long-lived keys. You copy a token out of your own browser session, and it lasts about a day. Sign in to da.live, open DevTools (⌥⌘I) → Network, filter for admin.da.live, reload the page, click any request, and copy the value after Bearer in the authorization request header.

Then, with that on your clipboard:

Terminal · reads straight from the clipboard, nothing to paste
security add-generic-password -a "$USER" -s da-token -w "$(pbpaste)"

And in ~/.zshrc, next to the Xray lines:

~/.zshrc
export DA_TOKEN="$(security find-generic-password -a "$USER" -s da-token -w 2>/dev/null)"

When it expires you'll get a clear message telling you so, rather than a confusing error. Just repeat the copy, run security delete-generic-password -s da-token, and add it again.

Check the key works

One minute

Terminal · in the repo
.claude/scripts/xray-api.sh check
You should see

auth OK followed by API OK. That's your key talking to Xray successfully. If it says a variable isn't set, your ~/.zshrc edit hasn't been picked up — open a fresh terminal.

Connect Claude Code to Jira

Three minutes

The agent reads tickets through Atlassian's MCP server. The repo already has the connection configured, but each person authenticates as themselves. Start Claude Code in the repo folder — it'll ask whether to enable the atlassian server. Say yes. Then:

In Claude Code
/mcp
You should see

A prompt to log in through your browser. Once you're back, atlassian shows as connected. The agent can now read EC tickets as you.

Do a dry run on something that already exists

Two minutes · this proves the whole chain works

BRANDS.json is a finished plan of 16 tests that are already live in Jira. Running it in preview mode touches nothing and confirms every piece is connected.

Terminal
node .claude/scripts/xray-push.mjs .claude/qa/plans/BRANDS.json --dry-run
You should see

0 to create, 0 to update, 16 unchanged, and the three test suites reported as in sync. That means the tooling found all 16 existing tests and correctly decided to leave them alone.

You may also see 16 adopted from Jira by label — that's fine and expected. It means your clone hadn't seen these tests before, so it looked them up in Jira rather than creating copies.

If it says "16 to create", stop

That would mean it can't recognise the existing tests, and running it for real would duplicate all sixteen. Don't run it without --dry-run. Ask before going further.

Your first plan

Setup done. Here's the actual working loop, which you'll repeat for every ticket.

Ask the agent for tests

In Claude Code, in plain English:

In Claude Code
use the qa-xray agent to write test cases for EC-22

It'll read the ticket, cross-check the design handover and the live site code, and then show you three things: a table of proposed tests, a coverage matrix mapping every acceptance criterion to the tests covering it, and a list of clarifications — the parts of the ticket that can't be tested as written.

That last list is often the most valuable output. Vague criteria like "must feel smooth" get flagged rather than quietly invented around.

Read it properly

The plan lands at .claude/qa/plans/<FEATURE>.json. It's a plain text file — open it, edit anything that's wrong, ask the agent to change things. This is the cheap moment to fix mistakes. Nothing exists in Jira yet.

You should see six tests, one for each thing we always check: authoring, functionality, visual, compatibility, accessibility and internationalization. Seven if compatibility split into desktop and mobile, which only happens when the two are genuinely different designs rather than the same design at two sizes.

Two things worth checking yourself: every acceptance criterion from the ticket should turn up in at least one step somewhere, and each test should list the fixture pages it needs. If a test cites a fixture that isn't in the plan, the push will refuse it — but it's nicer to notice now.

Build the test pages first

Your steps link to ready-made pages, so build those before the tests exist — otherwise anyone following a link gets a 404. Dry run first; it writes nothing.

Terminal
# see what pages would be built — writes nothing
node .claude/scripts/da-fixture.mjs .claude/qa/plans/MEGAMENU.json --dry-run

# build them for real
DA_FIXTURE_APPROVED=1 node .claude/scripts/da-fixture.mjs .claude/qa/plans/MEGAMENU.json

Then open one in a browser and check it looks right. This is worth thirty seconds — it's where you catch a fixture that's subtly wrong, which would otherwise look like a bug in the block.

Preview, then push the tests

Terminal
# see exactly what would happen — writes nothing
node .claude/scripts/xray-push.mjs .claude/qa/plans/MEGAMENU.json --dry-run

# do it for real
XRAY_PUSH_APPROVED=1 node .claude/scripts/xray-push.mjs .claude/qa/plans/MEGAMENU.json

# and check Xray actually counted it — linked is not the same as covered
node .claude/scripts/qa-coverage.mjs --plan .claude/qa/plans/MEGAMENU.json

The script prints the Jira key of every test it creates. It then writes a to-do list of things only Jira can do — issue links, labels — which the agent applies for you. Ask it to finish the job and it will.

That _APPROVED=1 bit isn't red tape. Anything that writes to Jira or to the client's content is blocked until a person types their approval into the command, so the agent can never do it on its own initiative.

Commit

Terminal
git add .claude/qa/plans/
git commit -m "Add plan file for MEGAMENU"
git push
Why this matters

The .result.json file records which plan entry became which Jira ticket. Committing it means the next person's changes update your tests instead of guessing. It's a safety net, not the only one — but don't skip it.

Four rules

Each of these exists because breaking it caused a real mess.

Never renumber a test id

BRANDS-TC-01 is how the tooling knows which Jira ticket a plan entry belongs to. Change it and you orphan a test and create a duplicate. Adding new tests? Give them new numbers on the end. Removing one? See the next rule.

Never delete a test to retire it

Deleting destroys its execution history — the record of every time someone ran it. Instead: --deprecate BRANDS-TC-09. That pulls it out of every suite so nobody runs it, and leaves the ticket and its history intact.

Always --dry-run first

It's free, it takes seconds, and it prints a line-by-line diff of what would change, including individual test steps. There is no reason to skip it.

Plans are named after features, not tickets

BRANDS.json, not EC-14.json. Tickets get renumbered and repurposed — it's happened here already, stranding thirteen tests. Features don't move. Each plan records which ticket currently specifies it, and that pointer can be updated for free.

When it looks wrong

What you seeWhat it means
XRAY_CLIENT_ID is not set Your ~/.zshrc hasn't loaded. Open a fresh terminal window.
MISMATCH The local record and Jira disagree about which ticket a test is. The script refuses to guess, because guessing would rewrite the wrong test. Ask before resolving it.
DUPLICATE Two Jira tickets claim the same test id. One of them shouldn't. Same advice — ask.
N adopted from Jira by label Completely normal. Your copy of the records was out of date, so it looked the tests up in Jira instead of duplicating them.
It wants to create tests that already exist Run with --adopt to rebuild the local record from Jira, then dry-run again.
Suite drift, unclaimed A test sits in a suite the plan no longer claims. It's only reported, never removed automatically. Have a look and decide.

The repair command, for a fresh clone or a lost record file:

Terminal · writes nothing to Xray
node .claude/scripts/xray-push.mjs .claude/qa/plans/BRANDS.json --adopt

And before each sprint, this checks whether any ticket behind a plan has been quietly repurposed:

Terminal
node .claude/scripts/spec-drift.mjs
