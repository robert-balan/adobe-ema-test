qa-xray · how it works

Spec to Xray

What happens between typing “write test cases for EC‑14” and real, linked, runnable tests appearing in Jira — and where you get to say no.

You type use the qa-xray agent to write test cases for EC-14
You get back, before anything is created
  • A draft test plan saved as a file on your machine
  • A table of every proposed test
  • A matrix showing which acceptance criterion each one covers
  • A list of gaps and things the ticket doesn’t make clear

First, the words

Six words you'll keep hearing

Xray adds its own vocabulary on top of Jira. These are the only ones you need.

Spec ticket
The ordinary Jira Story describing what should be built — EC‑14, for example. It carries the acceptance criteria the tests trace back to.
Xray Test
One Jira ticket holding one test: a precondition and a numbered list of steps, each with an action and an expected result.
Test Set
A named bag of tests — our suites. There are exactly three for the whole project: Sanity, Regression and E2E.
Test Plan
What you intend to run for a release or sprint. Draws from the sets.
Test Execution
One actual run. This is where pass/fail is recorded, per step. It is also the only thing that creates history worth preserving.
The plan file
.claude/qa/plans/BRANDS.json — the draft on your machine. This is the master copy; Jira is the published copy.
Fixture
A ready-made test page. Instead of a step telling you to go and build content, it gives you a link to open. The agent creates these for you in Document Authoring (DA), the tool authors use to write pages.

The sequence

Twelve steps, one of them yours

Every step is tagged with what it touches. Read the tags alone and you have the safety model: nine steps read things or write a local file, one step is your decision, and only the last two change anything in Jira.

00

Check the ticket still means what it used to

reads

Spec tickets in this project get repurposed. EC‑18 was the brand carousel one week and the Utility Bar the next, which stranded thirteen tests pointing at a spec that no longer described them. So the agent first compares what the ticket was called when the plan was written against what it’s called now, and stops if they differ.

01

Read the spec ticket

reads

The whole description, not just the acceptance criteria — these tickets carry variants, content slots, state modes and architecture constraints, and a lot of testable behaviour hides outside the numbered AC list.

02

Go and look at the real thing

reads

A spec says what should happen. Three other sources say what does. The agent reads the block’s real code and the real authored content from the public branch preview, and resolves every colour and size through the design handover. Where these disagree with the ticket, that becomes a question for the team — never a silent decision.

03

Inventory every acceptance criterion

working

Each AC is listed by its id and marked as functional, accessibility or authoring. Anything not objectively checkable — “must feel smooth” — is flagged as needing clarification rather than turned into a test nobody can fail fairly.

04

Design the cases

working

Every block is covered against the same six categories — authoring, functionality, visual, compatibility, accessibility, internationalization — so coverage is comparable across tickets. One test per category, 6–14 steps each, with compatibility splitting into desktop and mobile only where the two are different designs rather than one design at two sizes. Every acceptance criterion is covered by at least one step rather than by its own test: Xray scores steps independently, so per-criterion pass/fail survives the consolidation. Grouping by fixture is retired — fixtures are generated now, so a step simply cites the URL it opens.

05

Sort them into suites

working

Sanity is the thin smoke set — does it render, does the main path work, on both viewports. Regression is everything. E2E is the journeys that cross from one block or page into another. A test can be in more than one.

06

Write the plan file

writes a local file

Everything lands in one JSON file on your machine. Nothing has touched Jira. You can edit this file directly, and it stays the master copy for the life of the feature.

07

Check its own work

reads

A dry run validates the file against the schema and prints exactly what would be created, updated or left alone — including which suites would change. If the agent got the shape wrong, it finds out here rather than after forty tickets exist.

Stop

Nothing above this line reached Jira or DA. Nothing below it happens without you.

The agent presents the full proposal and waits. What you get:

  • A table of every test — its id, its category, its suites, the ACs it covers
  • An AC coverage matrix: every criterion and the test covering it, with any uncovered one called out and explained
  • Coverage gaps — behaviour worth testing that no AC mentions, added deliberately and labelled as such
  • Clarifications — ACs that contradict each other, can’t be measured, or disagree with the real code
  • The exact command that would apply it, and the text of any comment it would post

Approving is a sentence. Rejecting is a sentence. Asking for changes costs nothing, because the plan is still just a file.

08

Build the test pages first

writes to da

The steps link to ready-made pages, so those pages have to exist before the tests do — otherwise a tester follows a link and gets a 404. The agent builds them in DA under /drafts/qa/, one per situation you need to check: eight logos, two logos, one logo, a deliberately broken one, and so on.

Two things it cannot do, by design. It can't put a page anywhere outside /drafts/, and it can't publish — it only ever makes a preview. So a test page can't accidentally end up on the live site.

09

Create the tests in Xray

writes to jira

Only now do tickets appear. The push reconciles rather than blindly creating: a test in the plan with no ticket is created, one that matches is left alone, one that differs is updated in place — same ticket, same key, execution history intact — and one that has been dropped from the plan is reported for you to decide on, never deleted.

10

Wire up the Jira side

writes to jira

Xray’s API can write steps but not Jira fields or links, so a second pass adds the traceability link to the spec ticket, the labels, and a short “QA scope” comment so a tester knows what to run without reading any of this.

11

Report what actually exists

reads

Real ticket keys, verified against the API — not a restatement of what the script said it would do.

Conventions

Two naming rules, both learned the hard way

Titles are spec, then category, then name

Header: Products Brand Carousel - Accessibility - Keyboard, semantics and contrast — the ticket’s summary, then which of the six categories it belongs to, then the test’s own name. No ticket key, no AC numbers.

Why: tests are read in flat lists — suites, plans, execution boards — where the linked ticket isn’t visible. Leading with the spec title groups a block’s tests together, and the category tells you at a glance what a block is and isn’t covered for.

Ids are named after the feature, not the ticket

BRANDS-TC-01, not EC-14-TC-01. The id is how a re-run recognises an existing test, so it can never be renumbered once pushed.

Why: tickets get repurposed and renumbered; features don’t. When a spec moves, only one field changes — the pointer to the current ticket — and every test id survives untouched.

Afterwards

When the spec changes — and it will

You edit the plan file and re-run. Because tests are matched on their id, the same tickets are updated rather than duplicated.

SituationWhat the push does
In the plan, no ticket yetCreates it
In both, identicalLeaves it alone
In both, steps differUpdates in place — same key, history preserved
Has a ticket, dropped from the planReports it for review. Never deletes it
Genuinely obsoleteYou retire it with --deprecate: removed from every suite, flagged, ticket and history kept

Deleting is reserved for tests that have never been run. Once a test has an execution against it, deleting destroys the only record that it ever passed.

Limits

What it won’t do

—

It won’t invent acceptance criteria. Every test traces to something actually in the ticket. Behaviour that clearly needs covering but isn’t specified goes in a separate “coverage gaps” list for you to decide on.

—

It won’t write to Jira without approval. Writing the plan file isn’t a Jira write and needs no permission. Anything that creates or edits a ticket does.

—

It won’t claim success it hasn’t verified. Reported keys are read back from the API.

—

It won’t quietly pick a side. When the ticket, the code and the design disagree, all three are reported and the spec holds until the team decides.

—

It won’t pad a thin ticket. If the spec is vague or self-contradictory it says so, quoting the offending criterion, rather than generating dozens of low-value cases.

Reference

The commands you'll actually use

# is the Jira/Xray setup still what we think it is?
node .claude/scripts/verify-environment.mjs

# has a spec ticket changed since we wrote its tests?
node .claude/scripts/spec-drift.mjs

# build the test pages the steps link to — dry run writes nothing
node .claude/scripts/da-fixture.mjs .claude/qa/plans/BRANDS.json --dry-run
DA_FIXTURE_APPROVED=1 node .claude/scripts/da-fixture.mjs .claude/qa/plans/BRANDS.json

# preview every change to the tests — still writes nothing
node .claude/scripts/xray-push.mjs .claude/qa/plans/BRANDS.json --dry-run

# apply it, for real
XRAY_PUSH_APPROVED=1 node .claude/scripts/xray-push.mjs .claude/qa/plans/BRANDS.json

# did Xray actually count it? linked is not the same as covered
node .claude/scripts/qa-coverage.mjs --plan .claude/qa/plans/BRANDS.json

# retire a test without destroying its history
XRAY_PUSH_APPROVED=1 node .claude/scripts/xray-push.mjs .claude/qa/plans/BRANDS.json --deprecate BRANDS-TC-09

Those _APPROVED=1 prefixes aren't red tape. Anything that writes to Jira, or to the client's content, is blocked until a person types their approval into the command — so it's visible in the history, and the agent can't decide to do it on its own.
